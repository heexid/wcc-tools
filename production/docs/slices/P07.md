## Optimistic concurrency

| Piece | How |
|---|---|
| Version | `bookings.updated_at`: it moves only on a real edit, not on a recompute (P1), so an invoice added elsewhere doesn't count as a conflict; rule 10 still guards the total. |
| Sending it | The form keeps the version it loaded (`initial.updatedAt`) and the one each save returns, and sends it as `expectedUpdatedAt` with every save and save + invoice. |
| Checking it | `booking_errors()` (so the mock and the RPC agree, parity) **and again under the row lock** in `save_booking_tx`, so a save that commits in between is caught too. Result: `errors.booking = "conflict"`, a new value of the existing field, so no contract shape changed. Canceled still wins. |
| Notice | Copy approved 2026-11-16, recorded as INTERACTIONS **2.19**: warning alert "This booking was changed by someone else" — "Reload to see their changes. Your edits here haven’t been saved." + **Reload booking** (reloads without the leave prompt). **Figma note still to add.** |
| Mock | Same rule. Under the frozen test clock its `updatedAt` rarely changes, so the conflict is exercised on Supabase (two browsers) and in the parity vectors. |

## Security review (2026-11-16)

No findings at confidence ≥ 8. Verified:
- `search_booking_ids` builds its `EXECUTE` text only from fixed strings; every user value is bound through `USING`, so there is no SQL injection. It is security invoker, so RLS applies.
- The conflict check is reachable only through admin RPCs and runs under the row lock. Omitting `expectedUpdatedAt` only waives the caller's own protection.
- The profile RPCs are limited to the caller and gated by `is_staff()`.
- The proxy exemption is POST-only; enforcement stays in the database.
- No action uses the service-role key.

## Code review (2026-11-16, report-only, fixed by hand)

All 10 findings were real; all fixed:

| # | Finding | Fix |
|---|---|---|
| 1 | **Lost update:** items- or crew-only edits didn't move `updated_at` (derived-only recompute), so two editors could overwrite each other's items | Every save sets `updated_at = clock_timestamp()`; pgTAP 011 proves an items-only save moves the version and the stale save is refused |
| 2 | A failed list query left the skeleton forever | Retries every 10 s while failed (no read-error design exists) |
| 3 | Unguarded casts: `from=2026-02-31`, `page=1e20` failed every time | `try_date` / `try_num`; invalid dates compare as the prototype's strings; paging clamped |
| 4 | Create invoice with no unsaved edits sent no version → priced on a total the user never saw | The form sends its version; the RPC checks it under the row lock → conflict |
| 5 | Save committed, then the follow-up read failed → "couldn't save", and the retry conflicted with the user's own change | The write RPCs return the finished row (`booking_row`, `invoice_json`, migration 011): no second read |
| 6 | Under the lock only the version was re-checked; a concurrent cancel / invoice could slip through or surface as a connection error | Canceled re-checked under the lock; a check violation becomes `booking_invalid {total: below_paid, minimumTotal}` |
| 7 | Mock vs SQL differed on `expectedUpdatedAt: ""` | SQL treats empty as absent, like the mock |
| 8 | Parity never exercised the under-lock path or a real version change | pgTAP 011 (7 assertions) with real successive saves |
| 9 | Mock `listBookings` didn't clamp `pageSize` like SQL | Same 1–100 clamp and integer flooring |
| 10 | Midnight cookie deletion only on the redirect path | Cleared on every response path |

After the fixes: pgTAP 11 files / 169 on real Supabase · parity 102 / 65 / 68 · concurrency ✅ · unit 272.
