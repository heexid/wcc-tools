The invoice modal, `create_invoice` and the snapshot + hash were wired in P2 / P3 / P7. P9 moves the PDF to the server and stores it.

## How it works

| Piece | How |
|---|---|
| Route | `GET /api/invoices/<id or INV-number>/pdf` → `{ url, fileName }`, a **10-minute** signed URL (PRD §4.3) |
| Who | The invoice is read through the **caller's** session, so RLS decides: staff only, sessions end at 00:00 WIB. Anyone else gets 404. `/api/*` without a session → **401** (proxy). |
| Integrity | The snapshot is re-hashed (canonical JSON + sha256, same as the DB) and must equal `snapshot_hash`, else `500 snapshot_mismatch` → dialog 37 |
| Content | Figures from the snapshot **only**. Brand row / From block from the **current** business (US-14). Logo passed as a 2-minute signed URL. |
| Storage | Private bucket `invoices` (PDF, ≤ 5 MB, no API policies: only the server's service role touches it). Path `<number>/<business fingerprint>.pdf`. |
| Caching | Same business → stored file reused. Changed business → new fingerprint → re-rendered once. Missing file → regenerated from the snapshot. |
| Invoice row | Only `pdf_path` is set. `service_role` holds `select` plus `update (pdf_path)` only (pgTAP 012). The recompute trigger now fires only on `amount`, `voided_at`, `booking_id`, so a path change touches nothing else. |
| On confirm | After `create_invoice` the client quietly asks the route to render + store (PLAN §8 "generate on confirm"); a failure there changes nothing, the next download renders. |
| Failure | Any route error → the existing dialog 37 (Try again / Cancel); the invoice is never rolled back. Each failure stage is logged (no snapshot contents). |
| Wrapping | The server measures text with the PDF's own Inter files (fontkit), the same contract as the browser's canvas measure. |
| Mock | Unchanged: renders in the browser. |

## Security review (2026-11-16)

No findings at confidence ≥ 8. Verified:
- The service-role steps are reachable only after an RLS-filtered read with the caller's session; anon, inactive and expired-session callers get 404 / 401 first.
- `id` is only a filter; the storage path comes from the DB-constrained invoice number plus a hex fingerprint, so no traversal is possible.
- The logo is only ever a `branding` signed URL or an inline data URL, so there is no SSRF.
- Responses are generic and logs carry no PII.
- Logo uploads and deletes run with the caller's session under the admin-only policies.
- Both buckets are private; `service_role` can update only `pdf_path`.

## Code review (2026-11-16, report-only, fixed by hand)

All 10 findings were real; all fixed:

| # | Finding | Fix |
|---|---|---|
| 1 | A failed logo signing made the next business save delete the logo (null read as "removed") | Unsignable logo shows a blank-tile placeholder; an unchanged logo is left out of the update entirely |
| 2 | Fonts read from `public/` at runtime would be missing from the Vercel function bundle | `outputFileTracingIncludes` for the PDF route |
| 3 | A one-off logo-signing error stored a logo-less PDF for good | The route fails (dialog 37, retry) instead of storing it |
| 4 | Cache key ignored the template: layout fixes never reached stored PDFs | `PDF_TEMPLATE_VERSION` is part of the key (bump on any layout change) |
| 5 | Mock vs SQL paging still differed on `Infinity`, `1e400`, `""` | One rule in both; 4 more read-parity cases (76 / 76) |
| 6 | Dashboard retry kept firing after leaving the page | No retry once unmounted |
| 7 | Concurrent admin saves could point the business at a deleted logo | Unchanged logo is never re-written, so the DB keeps the newest |
| 8 | The expiry test never checked the route's own link | Decodes the route's token: exactly 600 s, `download` = invoice file name |
| 9 | Duplicate hash implementation; two sequential reads | Shared `sha256` / `stableStringify`; reads in parallel |
| 10 | Old-fingerprint PDFs were never cleaned up | The previous file is removed after a new one is stored |

Logs go through the P10 scrubber (no tokens, emails or phone numbers).
