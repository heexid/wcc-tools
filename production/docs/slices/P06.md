The query-shaped contract and the first SQL reads landed in P3 (migration 004). P6 makes them the production queries.

## What changed

| Area | Change |
|---|---|
| **Calendar loads only the visible range** | `BookingCalendar` reports its window to the page (`onVisibleRange`): month grid including the outside days (6×7), the week, or the day. The page queries exactly that, plus the filters. ‹ › fetch the next window; the previous rows stay until it arrives. The anchor stays in calendar state, as before, so arrow keys and fast clicks don't race the URL. |
| **Search on the trigram indexes** (migration 007) | Escaped `ILIKE` inline in `WHERE` on `booking_name`, `client_name`, `ref` (new GIN trgm index) and `client_phone`. The prototype's phone rule (contains the digits as `+62…` **or** in the local `0…` form) is rewritten as two index-friendly conditions: contains the digits, or starts with `+62` + the digits minus their leading 0 (proved equivalent; parity covers it). A literal `%`, `_` or `\` matches literally, like `String#includes`. Debounce (250 ms) was already in the UI. |
| **Rows only for what's returned** | Filtering and ordering run over ids (`ordered_booking_ids`). The full `BookingRow` JSON is built only for one table page or the calendar's window (P3 review #9). |
| Unchanged | Server-side sort + pagination, KPIs, Upcoming rail, insights (this week's rows), crew schedule, detail (`get_booking`), the URL contract (`useBookingFilters`), all markup. |

## Code review (2026-11-16, report-only, fixed by hand)

All 8 findings were real; all fixed:

| # | Finding | Fix |
|---|---|---|
| 1 | Profile RPCs ignored `active` / the midnight rule | Migration 009: `my_profile`, `update_display_name`, `mark_password_changed` require `is_staff()` |
| 2 | **Search never used the trigram indexes** (the empty-search `OR` + a reused CTE made the pattern a runtime value) | `search_booking_ids()` runs one `ILIKE` per indexed column through `EXECUTE … USING` (planned with the real pattern) as an uncorrelated candidate set. Verified on real Postgres: `Bitmap Index Scan on bookings_client_name_trgm` |
| 3 | Calendar / table waited for the whole dashboard round | List queries compute today themselves and start in parallel |
| 4 | Both list queries ran whatever the view | Each runs only for the view on screen |
| 5 | `get_crew_schedule` built rows for every past booking | Month count = count over ids; rows only for upcoming |
| 6 | A failed refetch showed the previous query's rows | A failed query goes back to its skeleton |
| 7 | Midnight sign-out could leave cookies if Auth's logout failed | Proxy deletes the auth cookies on the redirect itself |
| 8 | `pageSize: 0` divided by zero | Clamped to 1–100 |

Read parity still 68 / 68 after the rewrite.
